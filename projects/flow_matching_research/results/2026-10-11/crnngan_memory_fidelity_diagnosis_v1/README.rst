C-RNN-GAN 内存修复与完整训练一致性诊断
=======================================

两种缓存候选均未部署到35个完整500-epoch任务。原完整队列v3继续按32GiB物理可用、40GiB提交余量等待，原七种方法与五种子、3014首发布MIDI、10323257音符、350x2网络、batch20、完整课程100均保留。诊断不是缩短的基准实验，不增加独立训练种子或榜单指标。

第一候选删除重复空操作，复用一个空操作。两次真实完整首轮的19个变量均与原检查点逐位一致，但训练损失73856.66732271634与原73856.6647235577不同；匹配原BLAS环境后差异仍存在。图节点由5831降至5699，而冻结TF1.15源码的自动操作种子依赖图操作ID，因此后续课程随机序列等价未获证明，未采用。早先冻结配置中的“变量/损失比较失败”描述为联合判定，独立读取证实变量本身全部一致。

第二候选保留全部原图节点，仅规范化无依赖空fetch。真实完整四轮分别为长度4、8、12、16，每轮130批，共520预训练更新。原图节点定义、函数库和图版本全部逐位一致，NumPy和Python随机状态一致，前三轮全部训练变量及MIDI样本一致；第四轮8个G变量及MIDI样本不同，最大绝对变量差0.15422127023339272。退出由一致性检查失败引起，并非资源超限；峰值RSS3822518272、私有内存4638670848字节。静态TF种子定义相同不能证明状态性内核随机流相同，尚不能将差异归因于确定性调度或原实现自身。

原执行方式对照v1已完整执行首轮，但样本核验错误假定文件名始终以seed1103开头。作者代码实际使用输出目录basename；该已终止尝试及完整检查点保留。v2仅修正样本观察路径，保持原Session调用、科学参数、全量四轮和原资源守护，已实际启动native worker，四轮对照结论尚未获得。

独立checkpoint、全图、随机状态及MIDI诊断可使用scripts.flow_matching.diagnose_crnngan_epoch_states_v1重新执行；配置为configs/reproducibility/fm_crnngan_four_complete_epochs.2026-10-11_v1.json，输出必须选用新的保存路径，解释器使用冻结的原生Python3.7/TF1.15。56项相关验证通过，作者原代码有两条语法警告。完整训练登记闸门保持四轮完整状态一致要求，并检查真实图、参数规模、变量数量、130批和全部更新，未降低判定。

首轮原执行方式检查点已独立读取核验：130批、19变量、4924855参数、3014首MIDI，所有变量与原参照逐位一致，生成MIDI也一致。原执行方式标量损失73856.6984375与参照73856.6647235577不同；未安装缓存候选时也有标量差异。该证据不能解释或豁免第四轮训练状态差异。详见preserved_original_first_epoch_v1.json和corrected_original_native_execution_observation.json。
